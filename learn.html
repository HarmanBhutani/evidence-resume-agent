    • Tick Server 2 is 4× slower on round robin and watch its queue fill. Switch to least connections.
    • Crash server 2 with the health check at 10 s, then reset and try 1 s. Count the lost requests.
    • Crash server 2 on least connections. A dead server finishes nothing, so it always looks idle and keeps winning the pick until the health check removes it. This is sometimes called a "black hole".
    • Push traffic to 150 req/s: no algorithm helps when total capacity is too small.
    Say it in an interview: "Round robin is fine when servers are identical. When they aren't, least connections sends work where there is spare capacity. Either way, health checks decide how long a dead server keeps receiving traffic, so I'd keep them frequent and add retries for idempotent requests."

    Database deadlocks: two transfers, two rows, nobody moves

    A money transfer locks the row it takes money from, then the row it pays into. If transfer A→B holds A while transfer B→A holds B, each waits for the other forever. The database notices the cycle, aborts one transfer, and the app retries it. Locking rows in a fixed order makes the cycle impossible.

      Try this

      • Watch the two transfers: each grabs its first row, then waits on the other's. The check finds the loop and aborts the younger one.
      • Switch to lock lowest id first: B→A now asks for A first and simply waits its turn. No loop can form.
      • In the busy bank, set the check to 5 s. Rows stay frozen between checks and the waiting count climbs.
      Say it in an interview: "Deadlocks come from taking the same locks in different orders. I lock rows in a consistent order, for example SELECT … FOR UPDATE ORDER BY id, keep transactions short, and still retry with a small back-off on a deadlock error, because the database can abort any transaction."
